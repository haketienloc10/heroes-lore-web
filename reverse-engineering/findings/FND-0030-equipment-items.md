# FND-0030 — Equipment item records and inventory state

## Question

What source data and per-instance state are required to award or pick up categories 0–6, and why can those records not be treated as ordinary item stacks?

## Reference and method

- Reference JAR: `original/heroes-lore-v2.1.2.jar`, SHA-256 `7eb032297967f5d8382cc4f1ab5c3016459e01b235b42a3b88c6a8bfe46c5f61`.
- Static inspection used `javap -classpath original/heroes-lore-v2.1.2.jar -c -p ag ac by d f g k l m s` and the local `/itm/00`–`/itm/06` resources.
- No J2ME runtime comparison was performed.

## Source evidence

- `ag.q()` reads the category and item ID from opcode 11, then reads the signed quantity from the following opcode 21. At bytecode offsets 74–112, a positive quantity constructs one item through `ac.a(category, itemId, true, true)`, sets `d.b` on equipment instances, and calls `f.a(item, quantity)`. It does not construct `quantity` separate equipment objects.
- `f.a(ac, int)` checks capacity first. Categories 0–6 follow the non-stack branch (`ac.b[category] == false`) and occupy one inventory slot; the quantity is used for the preflight limit (99), while the equipment item's own count remains one. Stackable categories merge counts up to 99.
- `d.a(byte[], int, boolean)` parses the numeric item value, equipment byte, characteristic flag, signed enhancement count and four signed inclusive enhancement ranges. When the creation flag is set it calls `d.a(byte, byte[], byte[], byte)` to roll the selected enhancement slots. `g.a(min, max)` supplies the source inclusive range draw using the Java random stream.
- Ground pickup in `m.m97a()` reconstructs an item through the same item table factory. For equipment, it sets `d.b` when the item's characteristic flag is false.
- Equipment instance serialization retains `d.b`, `d.e` and four enhancement bytes. Subclasses add three bytes for categories 0–2 (`k.a`, `k.b`, `s.c`), one for category 3 (`s.c`), and none for categories 4–6. These are per-instance values, separate from the immutable numeric item definition.
- `an.c(byte)` initializes five equipment slots: weapon categories 0–2, then categories 3, 5, 6, and 4. Its class-6 starter uses categories 0/5/6/4 item 0; class 7 uses 2/5/6/4 item 0; class 8 uses 1/3/5/6/4 item 0. This setup creates the initial items without enhancement rolls.
- `by.a(int, int)` bytecode offsets 44–153 maps slot 0 to category 0/2/1 for class 6/7/8, maps slot 1 to category 3 only for class 8, and maps slots 2–4 to categories 5/6/4. It asks `f.a(category)` for matching inventory indices and passes them to `l`; `l` returns the selected index and slot to `by`. The selection callback checks `d.b` before calling `an.b(inventoryIndex, slot)`; a false flag shows the two source message lines (IDs 18/19) and does not equip. This corrects the broader category-to-slot compatibility model used for save validation: the native menu's offered choices are class-specific.
- `an.n()` sums the four signed enhancement bytes with byte wrapping. It derives max HP/SP from the class base, the corresponding enhancement total, and level; attack from weapon base/upgrade plus the class attack and first enhancement total; and defense from slots 1–4, upgrades, the class attack/enhancement term, and `level / 3`.
- `an.b(byte, byte)` swaps an inventory entry with its matching equipment slot. The old item returns to that inventory index, or the selected item is removed if the slot was empty.
- The native equipment-change path in `by` maps a selected slot to its source item category, asks `f.a(category)` for existing compatible inventory indices, then opens `l` to choose one; `l` calls `an.b(inventoryIndex, slot)`. No empty choice or standalone unequip command appears in this path, so an explicit unequip action is not supported by the inspected source flow. This is static evidence; the equipment interaction has not been replayed in J2ME.
- Each `/itm/NN` resource is a sequence of one-byte-length-prefixed records. Records contain a type byte, two length-prefixed text fields, a little-endian signed integer, a 12-byte equipment block and category-specific subtype bytes. The converter emits these numeric fields only; text remains in the locale tables.

## Web port

- M71 extracts a local numeric catalog for categories 0–6, creates source-shaped equipment state for event rewards and ground pickup, keeps equipment as one item per inventory slot, and serializes enhancement/subclass bytes through browser saves.
- M72 adds the five source slots, starter equipment for classes 6–8, inventory/equipment swapping from the system menu, backward-compatible browser-save persistence, and source-derived max HP/SP, attack, and defense calculations. The derived profile now feeds basic attacks and incoming melee/projectile defense. M73 uses weapon subtype bytes 0 and 1 for the source critical threshold and critical damage bonus; M136 uses weapon byte 2 and category-3 byte 0 for the source weapon/offhand proc checks. Equipment entries from pre-M71 browser saves receive a deterministic zero-enhancement instance state on load. Automated coverage checks class-6 starter values (72 HP, 60 SP, 16 attack, 5 defense), enhancement/upgrade terms, swapping, legacy state migration, and save validation.
- M142 updates the in-game equipment/inventory view to use the extracted localized item names, including the source unidentified label, instead of displaying category and item IDs. Slot labels now follow source order: weapon, armor, shield, helmet, shoes. The category mapping follows the extracted shop tables: category 6 is helmet and category 4 is shoes. A focused test guards the slot-label order. The [local Chromium capture](../../reference/screenshots/web-render/M142-inventory-menu/capture.json) and [screenshot](../../reference/screenshots/web-render/M142-inventory-menu/inventory.png) show the class-6 starting loadout with localized names and an empty bag; they do not exercise bag-item use or establish J2ME screen parity.
- M186 follows the source slot-first equipment-change path: the player selects one of five slots, then receives bag indices for that slot's class-specific item category; equipping uses the existing one-item swap behavior. The bag view remains available for consumables, and selecting gear there routes back through its equipment slot. Unidentified equipment remains selectable but the equip action returns to the slot view without changing loadout, matching the source `d.b` gate. Focused tests cover all three class weapon categories, class-8-only armor, the remaining slot categories, source inventory ordering, invalid slots, equipment records without instance state, and the unidentified-item rejection. The complete Vitest suite, typecheck, production build, converter tests and pinned JAR hash pass. No browser replay or J2ME screen comparison was made.
- The event capability check can now resolve positive category-0–6 awards from the loaded catalog. This addresses the item-category gate in map 76/script 7 in code; the full stream still needs runtime verification.

## Limits

- M186 adds the source slot-first, class-specific category selection path to the web equipment view. No standalone unequip action is evidenced in the inspected source classes. Exact screen/input parity remains unverified. M77 adds localized catalog names and shop, upgrade, identification, and orb-attribute services (see [FND-0033](FND-0033-shop-refiner-blacksmith.md)). M136 implements weapon/offhand proc behavior and active-skill attack elements with unit coverage; source runtime/RNG comparison remains open.
- M88 maps class-6 weapon, armor and head item IDs to source image groups and renders the starter weapon in a controlled New Game browser run ([capture manifest](../../reference/screenshots/web-render/M88-player-equipment-render/capture.json)). M151 adds weapon/effect palette variants. M304 implements the optional class-8 shield layer using `bt.f173b`, the `/c3/s` layout and matching `sN` atlas; class-7/8 assets and runtime appearance checks remain incomplete.
- `bt.j()` loads a shield sprite only for class 8 and selects its atlas through `f173b`. `WorldScene.updateHeroSprite()` now composes that layer when the complete c3 shield layout and atlas resources exist. The generated assets contain only c1 character layouts/atlases, so class-8 shield pixels and runtime behavior remain unverified; M340 now reports the class unavailable instead of substituting Ronin resources. This source review used checked-in decompilation and generated local files only; it adds no J2ME comparison.
- Bonus-roll RNG position and resulting values, equipment screen flow, and resulting combat stats have not been compared against a live J2ME run. M142's browser capture covers only the starting inventory/equipment view; M77 has no service-screen capture. Browser saves are not source RMS-compatible, and the category-6 event stream still needs runtime verification.
