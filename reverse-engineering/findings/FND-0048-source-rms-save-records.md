# FND-0048 — Source RMS save record layout

## Question

What byte layout does the game use for primary and special inventory save records, and which saved item fields can be represented by the web model?

## Reference and method

- Static inspection of the checked-in decompiled source under `reverse-engineering/decompiled/sources/defpackage/`: `m.java`, `an.java`, `f.java`, `ac.java`, `d.java`, `s.java`, `k.java`, and `bp.java`.
- Cross-checks use the matching local generated equipment catalog. No actual JAR, native RMS record, or pre-existing/local saved-game file was accessed. M362 separately captures current web-schema persistence through the ordinary UI in a disposable Chromium profile; its method and limits are recorded below.

## Source layout

- `m.o()` serializes four primary payloads in order: player state (`an.m26a()`), regular inventory (`an.f69a.m91c()`), flags/mode (`m.m104a()`), and map/tile (`mapId`, X, Y). Each payload is encrypted independently and preceded by an unsigned big-endian two-byte length. The class-specific stores are `/k`, `/s`, and `/w` for class IDs 6, 7, and 8; RMS naming in `at` adds the underscore. The special inventory is a separate `/o` record with its own two-byte encrypted-payload length.
- `m.p()` reads the three class stores in class order and opens the `a` selection screen with the available character summaries. The selector shows localized hero names, then previews the selected hero's level, completion value, and `cd.m[heroClassId - 6]` portrait before loading that character.
- `bp.a()` XORs each payload byte using the cyclic key `{5,11,8,81,3,20}`, starting at key index 1, then appends the low byte of the sum of the consumed key bytes. The web codec validates that checksum before returning payload bytes.
- The player payload starts with signed completion-points and level bytes; six big-endian ints; a signed combo byte; five shorts; five optional ten-byte equipment records; five optional skill records; the active-skill slot; and signed cumulative play seconds. Each present skill record contains its ID, rank short, two source constants, skill experience, and two signed skill-level pointers (`-1` means unassigned).
- Each inventory payload begins with a big-endian currency int and then one presence byte per slot. A present slot adds a ten-byte item record; absent slots add no item payload. `an` constructs 30 regular slots and 15 special slots.
- The flags payload is 128 game-flag bytes, 128 quest-flag bytes, and a signed mode byte. Flags are packed least-significant-bit first within each byte. The location payload is three bytes.
- `ac.a()` emits ten-byte item instances. Categories 0–6 store their mutable source flag, upgrade byte and four enhancement bytes; categories 0–3 also store the final subtype byte. The other subtype bytes for categories 0–2 are reloaded from the item definition, so decoding those records requires the local catalog.

## Web implementation

- `source-rms-save.ts` now encodes and decodes the cipher/checksum envelope, four primary chunks, the `/o` record, class store names, player fields, variable-length 30/15-slot inventory payloads, flags, and map/tile bytes. Its structured save wrapper exercises both records together in memory.
- `source-rms-items.ts` maps ten-byte source item records to the browser item/equipment shape. The typed inventory helpers preserve null slots and therefore retain source slot indices when callers provide the fixed-size slot vector.
- `source-rms-game-save.ts` maps source-backed fields between `GameSaveState` and `SourceRmsSaveState` and encodes/decodes both class stores entirely in memory. It maps the active web skill at `skillIds[0]` to the source active-slot pointer, preserves equipment order and inventory item order, retains occupied regular/special source slot indices as compact-array sidecar fields, and pads regular/special inventories to 30/15 source slots. It rejects legacy web saves without persisted equipment slots, skill sets outside the source five-slot limit, and decoded source fields the web model cannot retain. M342 advances this provenance for uniquely identifiable count changes, additions and removals, plus explicitly marked equipment swaps; ambiguous duplicate-stack changes discard it.
- M335 gives browser saves class-specific JSON keys corresponding to classes 6–8 while retaining the prior version-one global key for compatibility. The title Load Game page lists localized hero names in source class order, previews the selected class's generated portrait with level and source-derived completion percentage, and starts the selected record. A prior single global save appears in its hero's row without a storage migration write. The generated class-7/8 portrait files are transparent 1×1 images, matching the local asset limitation.
- M339 adds a versioned portable JSON wrapper for the two exact source-encrypted records. From the title Load Game page, a user can select a package file and import it through the RMS decoder and equipment catalog, or export the selected web save's primary and special records as hex. Package validation checks its format, class-specific primary store name, `_o` store name, record framing, and source checksums before writing the converted save to browser storage. Import supplies only the source-absent timestamp, south-facing direction, and category-7 quick-item defaults. M341 preserves source slot indices in compact web saves and proves byte-identical unchanged record round trips with synthetic records. M342 advances that provenance for modeled transitions and invalidates it when a compact-array change is ambiguous.
- M362 performs a normal New Game and in-game Save Game after the Reah reward, allocates the 12 earned attribute points to HP through the Status UI, waits for HP/SP recovery, and confirms the System menu’s “Game saved.” message. It closes Chromium and relaunches a second process against the same fresh temporary profile, opens the title Load Game roster, selects the single Ronin level-5/map-64 row, and compares 27 current-schema fields after restoration. There are no field mismatches; cumulative play time is also restored. The capture includes save confirmation, cold title, roster, and a settled six-second post-load world frame, with no page or console errors. The harness makes no direct browser-storage reads or writes and deletes its disposable profile after the run ([M362 capture](../../reference/screenshots/web-render/M362-current-save-cold-session/capture.json)).
- Import requires the local equipment catalog to rebuild equipment subtype bytes. The source format does not store the web save timestamp, player facing, or selected quick-item category; import assigns the caller's timestamp and defaults facing/category to the source constructor values (south/category 7). Browser inventory arrays remain compact for gameplay. Unchanged imports and unambiguous modeled transitions retain regular/special slot positions. Changed duplicate-stack arrays discard the sidecar because source `e()` can merge equal item types without the removal compaction performed by `d()`; later RMS export then safely packs the current items into leading slots.
- Focused tests cover signed values, item records, variable-length slots, malformed framing/checksums, flag packing, the special record, class-specific stores, and in-memory conversion in both directions.

## Limits

- Regular browser Save/Load remains the existing JSON format. The `.hlrms.json` file is a web interchange wrapper containing the two source record byte sequences in hex; it is not a native Java RecordStore database file. Import writes the converted save to the browser slot for that class. Web `savedAt`, facing, and selected quick-item category have no fields in the inspected native records. Slot advancement follows checked-in source methods for the modeled cases, but duplicate stacks or other ambiguous transitions invalidate provenance instead of claiming a native slot result.
- The class-specific browser keys model the source roster but do not use native RMS bytes. M362 verifies one current-schema class-6 save/load across a cold browser-process restart and shows the title roster; it does not test every legacy roster case or compare selection with native J2ME. The new portrait placement has not been visually compared with the source screen.
- Tests use reconstructed source layouts and synthetic records. The title Load Game file-picker import and download export are implemented in source, but there is no browser runtime capture, native RMS byte fixture, cold-session import/export replay, or J2ME save/load comparison; the adapter does not establish compatibility with an actual J2ME RecordStore. M362 validates only fields represented by the current web schema; ground drops and unimplemented systems remain outside its save comparison.
