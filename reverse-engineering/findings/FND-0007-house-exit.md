## Bytecode path

1. `ad.a()` loads the map collision grid from `/m/<heroClassId>/<map>.evt`, where the path component is `m.f272a`, then loads three auxiliary tables. `m.f272a` is the selected hero class (6–8), not a map region. `ad.e(byte[],int)` stores the 7-byte rows in `f21a`, the 3-byte command rows in `f22b`, and strings in `f23c`.
2. At the end of player movement, `an.d()` can call `ag.b()`. That method looks one cell ahead in `f13c`, takes the absolute value of a nonzero marker, and dispatches trigger type `3`.
3. `ag.a(byte,byte)` indexes the 7-byte group by `abs(marker)-1`, selects a matching two-bit trigger type, checks the two packed flag references against the game/quest bit arrays, and rejects rows that need an unavailable inventory predicate. The last byte selects a script in `f22b`. Its `ag.a(byte[])` predicate treats item-category byte `-1` as no gate; otherwise it passes the category, item ID, and count bytes to `f69a.m90a(byte,byte,byte)`. Those three values remain signed Java bytes, and the inventory checks the matching stack count against the signed minimum.
4. `ag.i()` handles script command `7` followed by command `8`: command `7` carries the destination map and entry-direction index, and command `8` carries hero tile X/Y; it calls `m.b(map,directionIndex,x,y)`. The second command-7 byte is not a region ID ([M167 correction](FND-0039-newgame-map3-map4-route.md#opcode-7-arrival-facing-m167)). `m.b(byte,byte,byte,byte)` stores that map-change request for the world update.

## Map-64 route data

The south corridor ends at map cell `(9,18)`; the cell immediately below it, `(9,19)`, has signed collision value `-1`. On map-64 event table `/m/6/64.evt`, marker group 1 has a matching type-3 row:

```text
trigger row: [192, 0, 0, 255, 0, 0, 0]
script 0:    [..., [7, 0, 1], [8, 26, 24], [99, 0, 0]]
```

The top two bits of `192` select trigger type `3`; both packed conditions refer to game flag 0. Byte 3 is `255` (`-1`), so this row has no inventory predicate. Script commands `7` and `8` request map 0 with entry-direction index 1 and hero tile `(26,24)`. The map's event bundle path remains based on the selected hero class, independently of that entry direction. The single source run reaches map 0 after the second Down hold; its console has `map : 64` followed by `map : 0`, and its screenshot places the hero at the town-side house entrance. The correspondence establishes the event path for this fixture; the exact complete game-flag initialization sequence has not been traced. The browser seeds flag 0 for this known post-New-Game scene based on the recorded route.

The source `.evt` resource also contains other trigger groups and a separate final four-byte operation table. Those other triggers/commands are not treated as equivalent to this map-change path. The extractor preserves them as data; the browser executes a capability-checked subset of the ordered event interpreter, while broader trigger and command behavior remains incomplete.

M300 keeps the item's three row fields in signed-byte form when evaluating inventory predicates, matching `ag.a(byte[])` and `f.m90a(...)`. A synthetic row with raw count byte `255` verifies Java's `-1` comparison against an existing stack; the current generated class-6 trigger tables contain no high-bit item fields. This is static-source and unit-test evidence, not a runtime comparison.

The type-3 exit row proves game flag 0 is set when the recorded route reaches the boundary. Under the browser's inferred flag set containing only bit 0 (other active bits are unknown), the first matching startup descriptors select block 1 on map 64 and block 2 on map 0. Source opcode dispatch confirms the action records mutate map/collision, decoration, and NPC state; M46 ports initial action-block opcodes 100–105, M47 adds 110, and M48 adds 109 and corrects opcodes 102/103 to the source decoration array (see [FND-0023](FND-0023-map-startup-operations.md)). This does not establish which action block the original runtime selects for every HOUSE-EXIT-001 state. FND-0008 traces the fresh-game routine that clears the bit arrays and sets flag 0 for the implemented New Game route. The map-64 transition script begins with opcode `9` setting game flag 3, then opcode `26` logging its BGM marker, followed by the map change. The browser applies that flag mutation. Broad command coverage was added after this finding; the current structural audit and runtime limits are recorded in [FND-0024](FND-0024-opening-cutscene-interpreter.md) and [FND-0027](FND-0027-supported-interaction-cutscenes.md).
