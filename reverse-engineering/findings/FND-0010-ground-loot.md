# FND-0010 — Enemy ground drops, pickup, and inventory insertion

## Scope and evidence

This finding traces ordinary enemy death loot and event-driven item transactions from the pinned v2.1.2 source and records the current browser port. Static source inspected in JADX is `ak.java`, `ad.java`, `ag.java`, `m.java`, `ar.java`, `f.java`, and `ac.java`; the enemy triplets are extracted without rewriting from `/enm/data0..2`. Browser evidence is the seeded M32 run; it is not a J2ME comparison.

## Verified source behavior

- `ak.l()` first rolls an inclusive integer from 1 through 150. It subtracts the third byte of each enemy drop triplet in order. At the first cumulative crossing, a triplet with weight 1 gets another inclusive 1–100 roll and succeeds at 20 or below; other weights select immediately. A failed one-weight candidate leaves the loop running, so a later candidate can be selected.
- The selected first and second triplet bytes are passed as item category and item ID to `ad`. Category 22 is explicitly ignored by the ordinary ground-item insertion overload. A separate death roll can insert category 11, item 0, with chance `20 + enemyRecord.f - playerLevel`; this is independent of the weighted item roll.
- A separate inclusive 1–100 roll drops currency at 60 or below. Its ground record stores `enemyRecord.f * 3`; `m.m97a()` multiplies the recovered amount by nine when the player picks it up.
- Ground records hold map tile, category/item or currency fields, and a 120-count timer. `ad.o()` decrements the timer once per map update and removes the record after it goes below zero. The marker blinks during the last 16 counts: it is drawn when the count exceeds 16 or is not divisible by 3. `/img/etcui/9` is the item marker and `/img/etcui/10` is the currency marker.
- Raw key 53 first calls `m.m97a()`. Pickup searches the player’s current tile. Currency is always accepted; an item is removed only if its destination inventory accepts it. If pickup fails, the input continues to the ordinary action path.
- `f` contains 30 inventory slots. `ac.f1b` marks categories 7–17 and 22–23 as stackable. Stack counts cap at 99; non-stackable items require an empty slot. The separate special inventory path for category 22 is not represented by the ordinary item-drop list.
- `ag.q()` reads the opcode-11 item category and ID into Java `byte` locals before opcode 21 supplies the signed quantity. High-bit category or ID bytes therefore decode as negative values rather than unsigned item indices; the command then applies to the regular `f69a` inventory.

## Browser implementation

- `web/src/world/loot.ts` preserves raw category/item IDs, performs the source selection and independent rolls, models the 30-slot/99-count insertion rules, advances marker lifetime/blink state, and applies the currency pickup multiplier.
- `WorldScene` rolls drops at the lethal-hit transition, renders the extracted source markers at the enemy tile, expires them on the 71 ms map-update cadence, and tries pickup before basic attack on Numpad5. Wallet and raw inventory stacks are stored in the existing version-one save format; older saves default to wallet 300 and an empty inventory.
- Current drop rolls use the `JavaRandom.nextSourceRange()` stream wired through `WorldScene.rewardDefeatedEnemy()` to `rollEnemyDrops()`. The generator matches the source bounded-range algorithm but uses time-dependent runtime seeds; its sequence has not been compared with J2ME. M32's seeded browser capture predates that RNG wiring and remains evidence for pickup behavior, not current drop-sequence parity.
- M32 loads a seeded save at map 27/tile `(9,5)`, defeats enemy 24 at `(10,5)`, steps onto that tile and picks up a currency drop. Saved wallet changes from 300 to 327, consistent with the source reward code 1, ground amount 3 and ninefold pickup. The [manifest](../../reference/screenshots/web-render/M32-enemy-loot/capture.json) and [capture](../../reference/screenshots/web-render/M32-enemy-loot/after-kill.png) record the route.
- Automated tests cover the weighted branch, failed rare candidate continuation, independent category-11 roll, coin multiplier, stacking, full inventory, timer expiry, marker blink, and legacy save defaults.
- M212 models the source's second 15-slot inventory for category-22 items. The browser save parser defaults this field to empty for earlier version-one saves; ground pickup routes category 22 into that list and keeps the ground item when the special inventory cannot accept it. Ordinary event item transactions continue to use the source's 30-slot inventory. Focused tests cover separate storage, capacity rejection, and save migration.
- M299 corrects the source inventory distinction. The trigger-row predicate is `ag.a(byte[])`, which calls `an.f69a.m90a(category, id, count)` for every item category, including 22. The special-inventory branch in `ad.a(byte, byte)` instead checks whether a category-22 map item can be collected; it is not the event-trigger selector. Opcode 11/21 item changes also use `f69a` in `ag.q()`. The web selector continues to check the regular inventory, with a synthetic category-22 regression guarding this behavior. The generated class-6 trigger tables contain no category-22 predicates.
- M301 decodes opcode-11 category and item ID bytes with Java signed-byte semantics before equipment lookup and regular-inventory quantity changes. A synthetic command with raw item ID 200 decodes to -56: the event capability gate rejects it, and direct interpreter execution reports `unsupported` without changing inventory. A scan of the 72 extracted class-6 event bundles found 54 opcode-11 commands and no high-bit category or item ID values.
- M306 checks whether the 15-slot `f73b` category-22 inventory has a native list screen. `l.a(Graphics)` can render negative slot IDs from `f73b`, but every checked-in `new l(...)` call supplies IDs from `f69a` or `an.a(ac)`, which returns a regular inventory index or an equipped-slot ID (100–104). The native callers therefore never pass a negative special-inventory index to that renderer. `f73b` is initialized, restored/saved separately, checked for category-22 map-item capacity, and populated by `m.m97a()`; no source menu exposes it. The web port's lack of a category-22 inventory screen is source-faithful, while acquisition/runtime comparison remains open.
- M307 preserves pickup feedback. `m.m97a()` queues “Gain <amount> G” for currency or “Gain <category name>” for items; if `ad.a(tileX, tileY)` finds no eligible item but `ad.m8a(tileX, tileY)` finds one on that tile, it instead queues `bg.t` (localized string 2375, “no space”) and returns false, allowing the ordinary action path to continue. The browser resolves category names from `itm/itmtp.tdf`, draws the matching centered message panel on success or capacity failure, and still falls through to the action after a failed pickup. M307 initially modeled the 16-frame queue as 16 world updates; M308 traces the source scheduler and confirms that nominal 71 ms interval matches the requested gameplay paint cadence.
- M308 traces the pickup message countdown through the checked-in `m`, `bd`, `br`, and `ar` code. The Options menu cycles `f163a` through indices 0–2, which map to 8/10/14 FPS in `br.a`; its extra 18 FPS table entry is not selected by that menu. `m.a(2, 2, 1)` enters gameplay and retains the selected frame-rate setting, defaulting to index 2 (14 FPS). `ar.a(Graphics)` decrements the queued 16-frame notice once per gameplay paint. In the browser, `gameSpeedScale()` scales elapsed simulation time by selected FPS / 14, and the notice decrements on each 71 ms world update; that gives the same nominal 16-interval lifetime for the selected 8/10/14 FPS values (2,000/1,600/1,136 ms). This resolves the scheduler-rate uncertainty without claiming paint/update phase or J2ME runtime parity.

## Limits and follow-up

M32's seeded browser capture predates the current JavaRandom drop wiring and therefore doesn't verify the present roll sequence; that sequence has not been matched against the J2ME runtime. The capture demonstrates currency pickup, while raw item pickup is covered by deterministic unit tests. M212's category-22 storage path is source-backed but has no browser replay because the inspected enemy-drop insertion path discards that category. M299's synthetic test covers a source branch not used by current generated triggers. M301's scan covers the 72 extracted class-6 event bundles only; other class tables and event data missing from the pinned JAR are outside that scan. M306 establishes that adding a category-22 inventory screen would not match any checked-in native menu path; item-acquisition and runtime comparison remain open. M307 models success and “no space” feedback; M308 confirms its modeled 71 ms countdown interval matches the source's requested 14 FPS gameplay loop, while paint/update phase and visual/J2ME comparison remain unobserved. Other item acquisition/use paths and the ordinary inventory UI still lack J2ME comparison. The enemy drop table is data-driven for all three variants, but the current world uses the fresh-game Ronin `data0` table.
